# Multi-Agent Restaurant Management System: Bridging Cloud AI to On-Premises Operations with IoT Core and MCP

## Abstract

Restaurant operations depend on systems that live behind the store's firewall — point-of-sale terminals, kitchen equipment controllers, inventory databases, and scheduling software. These systems cannot accept inbound connections from the internet, yet a new generation of cloud-hosted AI agents needs to query and act on them in real time. This project addresses that fundamental connectivity gap: **how do you let cloud-based AI agents invoke tools on a store's local network without opening any inbound ports, installing VPNs, or compromising the store's security posture?**

The solution is a three-layer architecture built on AWS. In the cloud, Amazon Bedrock AgentCore hosts a supervisor agent and four domain-specific secondary agents (POS, equipment, inventory, and scheduling). Each agent has access to tools — like "get today's sales" or "check the walk-in cooler temperature" — that appear to be local function calls. In reality, those calls are transparently routed through a Cloud MCP Gateway (implemented as AWS Lambda functions) that publishes commands over **AWS IoT Core's MQTT message bus** to the target store.

**MQTT is the linchpin of this design.** It was chosen over alternatives like SQS polling or API Gateway WebSockets for several reasons. First, MQTT is purpose-built for device communication — it supports persistent outbound connections from the store, meaning no inbound firewall rules are ever needed. Second, IoT Core provides built-in device identity through X.509 certificates, giving each store mutual TLS authentication without managing a separate identity provider. Third, MQTT's QoS 1 (at-least-once delivery) combined with IoT Core's message queuing means that if a store goes offline — a common reality in restaurant networks — commands wait in the queue and are delivered when connectivity returns. Finally, IoT Core's Device Shadow feature gives cloud agents a fallback: even when a store is unreachable, agents can read the last-known state (cooler temperature, POS status, equipment health) from the shadow, providing managers with a recent snapshot rather than nothing.

On the store side, a lightweight gateway process maintains the outbound MQTT connection and routes incoming commands to local **MCP (Model Context Protocol) servers**. MCP provides a standardized tool interface — regardless of whether the underlying system is a REST API, a serial port, or a proprietary controller, it gets wrapped in the same schema. This means the cloud agents' tool definitions remain consistent across hundreds of stores with potentially different hardware.

To develop and test this architecture without requiring physical restaurant hardware, the project includes a **restaurant simulator** — a Python application that models realistic restaurant operations: order generation following daily peak/off-peak patterns, kitchen equipment with thermal drift and random failures, inventory depletion with waste events, and employee shift management with labor cost tracking. The simulator exposes the same MCP tool interface and MQTT bridge as a real store, making it indistinguishable from the cloud agents' perspective. It also provides a REST API (14 endpoints), a WebSocket-driven React dashboard for visual monitoring, and a virtual clock with 1x–60x speed control so developers can simulate a full day of operations in minutes.

The key architectural decisions are:

- **Outbound-only connectivity** — stores never accept inbound connections; all communication is initiated by the store's MQTT client connecting to IoT Core on port 8883.
- **Per-store isolation** — each store is an IoT Thing with its own certificate, scoped to its own MQTT topic namespace (`stores/{store_id}/*`). One store cannot see another's data.
- **Protocol-level resilience** — MQTT QoS 1 with idempotent command processing (duplicate command IDs are tracked and skipped) handles the unreliable network conditions common in restaurant environments.
- **Tool abstraction via MCP** — the Model Context Protocol decouples the cloud agents from store-side implementation details. A store can swap its POS vendor without changing the agent layer.
- **Simulator as first-class integration target** — the MQTT bridge is not an afterthought; it is built into the simulator from day one so that the full agent-to-store pipeline can be validated before any physical deployment.

The system is designed for multi-store scalability (hundreds of locations), security by default (mutual TLS, least-privilege IAM, no sensitive data in the agent pipeline), and graceful degradation (Device Shadow fallback, message queuing, independent store lifecycles). It targets restaurant managers as end users — not diners — helping them answer questions like "How did we do on food cost this week?" or "Which equipment needs maintenance?" by letting AI agents reach into the store and pull the answers directly from the source systems.
